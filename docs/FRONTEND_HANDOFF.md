# 프론트엔드 연동 인계 · 2026-09-25

현재 `web/`는 React/TypeScript 모바일 웹 데모입니다. 백엔드 API, 지갑, Midnight SDK 호출은 연결하지 않았습니다. 아래 API/이벤트 이름은 **협의용 제안**이며 구현된 API가 아닙니다.

## 현재 구현과 미구현

| 영역 | 현재 프론트엔드 | 실제 서비스에서 필요한 작업 |
|---|---|---|
| 행사 입장 | 고정 행사와 QR 인증 완료 문구, 입력 화면 이동 | 행사 조회, QR/참가권 검증, 만료·중복·잘못된 행사 처리, 세션 발급 |
| 프로필 | 2단계 입력: 닉네임·나이·성별 / MBTI·SNS ID·20자 자기소개·사진 준비 | 서버 저장/검증, 조회, 수정 저장·취소, 필드별 공개 범위 확정 |
| 사진·AI | 버튼 클릭으로 준비 상태, 타이머 후 고정 이미지·4줄 분석 표시 | 파일 선택·업로드, AI 작업 생성/조회, 실패/재시도, 원본 삭제 및 보관 정책 검증 |
| 내 정보 | 프로필 카드, 수정하기 → 기존 입력 폼 | 새로고침 복구, 수정 API, 재분석 조건, 저장 전 초안 분리. 현재 입력 즉시 메모리가 변경됨 |
| 피드 | 2명 고정 예시, AI 이미지·인상 소개, 필터 | 행사별 실제 목록/페이지네이션, 추천 기준, 참가자 수, 차단·비공개 처리 |
| 호감·매칭 | 받은/보낸 탭, 중복 전송 방지, 상호 호감 성사 팝업 | 서버/계약 판정, 중복 요청 키, 동시 전송, 상대방의 후속 호감 실시간 수신, 전송 실패·확정 대기 |
| 익명 대화 | 매칭 상대별 로컬 메시지·목록, 미매칭 경로 차단 | 서버 접근 권한, 실시간 송수신, 읽음/순서/재연결, 저장·삭제, 차단·신고·대화 종료 |
| SNS 공개 | 로컬 동의/취소/대기와 상대 동의 시뮬레이션, 예시 완료 화면 | 실제 양측 동의 검증, 암호화 보관/키 전달, 철회·만료, 허용 후에만 복호화/조회 |
| 과금·행사 종료 | 미구현 | 무료 대화 범위, 연장 결제 여부, 행사 후 대화/SNS 접근 정책 |

모든 입력·메시지·호감·동의는 React 메모리 상태이며 새로고침하면 초기화됩니다. 사진 버튼은 파일을 읽거나 업로드하지 않습니다. 입력한 SNS ID는 메모리의 프로필에 있지만 실제 SNS 공개 데이터로 사용하지 않습니다. `/me`를 새 세션으로 직접 열면 예시 프로필을 표시합니다.

현재 SNS 요청 버튼은 **방의 전체 메시지가 4개 이상**이면 노출됩니다. 이는 데모 조건으로, 양쪽 각각의 발언 수나 과금 기준을 검증하지 않습니다. 운영 정책 확정 후 서버에서 판정해야 합니다.

## 백엔드 담당자와 결정할 것

1. **행사·사용자 식별과 세션**: `eventId`, 행사별 가명 `participantId`, 계약 handle, `matchId`, `conversationId` 매핑과 인증 방법. 참가권 소유와 API 세션 소유를 어떻게 연결할지 결정합니다. 새로고침·다른 기기 복구와 행사 종료 시 만료 기준도 필요합니다.
2. **공개 프로필과 비공개 데이터 분리**: 피드 DTO에는 이미지 URL, 인상 소개, 키워드, 허용된 기본정보만 포함합니다. SNS ID·원본 사진·비밀키는 포함하지 않습니다. MBTI 실제 16개 값 검증, 닉네임 중복, 자기소개/나이 제한을 확정합니다. 나이 입력은 나이 인증이 아닙니다.
3. **AI 파이프라인**: 업로드 허용 형식/크기 → 분석/이미지 생성 작업 → 완료/실패 상태 → 결과 URL/문구를 합의합니다. 이미지 방향은 밝은 파스텔 배경·밝은 의상이며 검은 텍스트가 읽혀야 합니다. 외모 묘사와 사용자 자기소개는 분리합니다. 원본 삭제 시점, 실패 작업/로그/백업/외부 AI 제공자의 잔존 데이터 처리를 합의합니다.
4. **호감과 매칭**: 받은 호감에 보낸 사람을 표시하는 현재 UI가 개인정보 정책과 맞는지 결정합니다. `like.created`, `match.created` 같은 수신 이벤트, 정확한 한번 처리, 중복 클릭·재시도·오프라인 대응이 필요합니다. 매칭 확정 후 팝업과 대화방을 생성해야 하며 클라이언트 계산을 권한 근거로 쓰면 안 됩니다.
5. **채팅**: REST + WebSocket/SSE 등 전송 방식, 메시지 ID/시간/순서, 재전송 중복 제거, 읽음, 이력 페이지네이션과 보관 기간. 매 요청/구독에서 행사·매칭 참여자를 확인합니다.
6. **SNS 동의**: 요청/대기/양쪽 승인/취소/종료 상태와 동시 취소·승인 충돌을 정의합니다. UI의 “관리자도 확인할 수 없어요”를 충족하려면 평문을 서버가 받는 설계로는 부족합니다. 브라우저 암호화와 키 관리 주체를 Midnight 담당자와 공동 결정해야 합니다. 한번 상대에게 전달된 정보는 취소로 회수할 수 없다는 경계도 합의합니다.
7. **공통 응답**: 행사 만료, 인증 만료, 호감 한도, 이미 처리됨, 매칭 없음, 동의 미완료, AI 실패 등에 대한 오류 코드와 UX 재시도 가능 여부. 로딩·빈 상태·실패 화면 연결에 필요합니다.

### 연동 인터페이스 제안

| 기능 | 협의용 인터페이스 | 필요한 응답/이벤트 |
|---|---|---|
| 입장 | 행사 조회 / 참가권 교환 / 내 세션 조회 | 행사 상태, 참가자 ID, 만료 시각 |
| 프로필 | 내 프로필 조회/저장/수정 / AI 작업 생성·조회 | 공개 카드 버전, 생성 상태, 이미지/소개/키워드 |
| 피드 | 행사 피드 조회 | 커서, 참가자 수, 공개 카드, 내 호감/매칭 상태 |
| 호감 | 호감 전송 / 받은·보낸 목록 조회 | 요청 ID, 처리·계약 확정 상태, match ID |
| 대화 | 대화 목록/이력 / 메시지 전송·구독 | 메시지 ID/순서, 읽음, 매칭 취소/종료 이벤트 |
| SNS | 동의 요청/승인/취소 / 승인 결과 조회 | 상태 버전, 양측 승인 여부, 승인된 암호문/키 전달 절차 |

API 명세와 예시 성공·실패 응답을 먼저 고정하면 `web/src/state/session.tsx`의 로컬 상태를 어댑터로 교체할 수 있습니다.

## Midnight 담당자와 결정할 것

근거: `contract/src/festival-match.compact`. 현재 계약 1개는 행사 1회입니다.

| 현재 회로/원장 | 연동 전에 확인할 사항 |
|---|---|
| `issueTicket`, `tickets: MerkleTree<10>` | 운영자 티켓 발급/전달, 중복 발급·분실, 참가자 witness 경로 공급/갱신, 트리 용량에 맞는 행사 인원 |
| `joinEvent(cardHash, instaCommit, dhPk)` | 카드 직렬화·해시 버전 규칙, 공개 카드 원본 저장소와 무결성 검증, Instagram/SNS ID 정규화·32바이트 인코딩과 salt 관리 |
| 티켓당 카드 1회 등록, 카드 갱신 회로 없음 | 현재 UI 수정하기와 충돌. 카드 해시/공개키/SNS 커밋 수정 허용 범위와 새 회로 필요 여부, 기존 매칭 영향 |
| `like(peer)`, `pendingLikes`, `matches` | 프론트 상대 ID와 handle 매핑, pairSecret 생성/검증, maxLikes·eventEnd 처리, 중복/동시 요청 및 확정 시점 |
| `revealContact(tag, ciphertext)` | 매칭 참여자의 암호문 1회 게시만 검증. **별도 양측 SNS 승인·동시 교환은 보장하지 않음.** 동의 회로/승인 버전/키 해제 절차를 새로 설계할지 결정 |
| `contacts: Bytes<96>` | 암호화 알고리즘, nonce/tag/평문 길이와 패딩, 키 파생, 가입 당시 커밋과 공개 값 검증 주체. UI의 SNS ID 최대 30자와 실제 인코딩 길이 일치 확인 |
| 행사 종료 검사 | 종료 후에는 like/revealContact가 거절됨. 이미 열린 채팅·이미 받은 SNS·새 공개 요청의 행사 후 정책과 정합성 확보 |

추가 공동 논점:

- 지갑 연결을 참가자에게 요구할지, 증명 생성/트랜잭션 제출/수수료를 누가 담당할지, 모바일 증명 지연과 실패 복구.
- 티켓 비밀·DH 개인키·salt·pairSecret의 생성/보관/복구 위치. 서버/운영자가 이를 아는지에 따라 익명성 보장이 달라집니다.
- 현재 공유 비밀을 아는 상대가 일방적 호감을 추론할 수 있습니다. 받은 호감에 상대 카드를 표시하는 UI와 “익명 전달”의 정확한 의미를 합의해야 합니다.
- 공개 원장에는 가명 카드·호감 카운트·매칭 참여자·암호문이 존재합니다. `like`의 `peer`도 `disclose`합니다. 누구에게 어떤 연결 정보가 보이는지 원장/트랜잭션 관측 범위를 함께 검토해야 합니다.
- 프론트 공개 완료는 트랜잭션 제출 직후가 아니라 합의한 확정/승인 상태 이후에 표시합니다. 계약 미확정·실패와 서버 인덱싱 지연의 상태 모델이 필요합니다.

## 우선 합의 순서와 완료 조건

1. **세 담당자 공동**: 행사/가명 ID, 받은 호감 공개 범위, SNS 동의·암호화 책임, 행사 종료/무료 대화 정책.
2. **백엔드 + 프론트**: DTO/오류/이벤트 명세, 프로필·AI·호감 API를 연결하고 새로고침 복구 확인.
3. **Midnight + 백엔드**: 티켓 발급부터 매칭 확정까지 연결, SNS 별도 승인·키 전달과 프로필 갱신 설계.
4. **통합 검증**: 두 기기/두 계정에서 한쪽 호감만으로 대화가 열리지 않는지, 양쪽 호감 후 각각 알림을 받는지, 한쪽 SNS 동의만으로 평문/복호화 키가 전달되지 않는지 검증. 재시도·동시 요청·만료·새로고침도 포함.

프론트 코드의 경로 차단과 데모 동의 시뮬레이션은 보안 검증이 아닙니다. UI의 “QR 인증 완료”, “사진 즉시 삭제”, “관리자도 확인 불가” 문구는 현재 제품 목표이며 운영 배포 전에 실제 구현과 일치시켜야 합니다.

## 실행·검증

- `npm run dev`: 로컬 프론트엔드 실행, `/preview`에서 화면 선택.
- `npm run build`: TypeScript 검사와 프로덕션 빌드.
- `npm run test:web`: Chromium/WebKit 64개 테스트 통과(2026-09-25).
- 이번 프론트 변경에서 계약/Devnet 연동 검증을 새로 수행한 것은 아닙니다.
