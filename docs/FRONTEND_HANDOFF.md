# ZKiss MVP 연동 인계 · 단일 축제 해피패스

이번 데모는 **하나의 축제에서 프로필 생성 → 호감 → 상호 매칭 → 익명 대화 → SNS 상호 공개**가 이어지는 것을 목표로 합니다. 운영 서비스 전체를 구현하는 것이 아닙니다. 아래 내용은 이전 인계 문서의 확대된 범위를 대체합니다.

현재 프론트엔드는 화면과 메모리 기반 예시 동작까지 구현되어 있습니다. 백엔드·Gemini·Midnight 실제 연결은 앞으로 진행할 작업입니다.

## 확정한 범위

| 항목 | 이번 데모에서 할 일 | 담당/협업 |
|---|---|---|
| 행사 입장 | 현재 데모 진입 화면 유지. 실제 QR 발급·스캔·인증은 구현하지 않음 | 프론트 추가 작업 없음 |
| 프로필 | 입력한 프로필 데이터와 AI 결과의 저장·조회 연결 | 프론트 + 백엔드 |
| AI 인상 분석 | Gemini API로 사용자 사진을 실제 분석하고 소개 문구를 표시하는 방향 | 프론트 + 백엔드, API 호출 담당 합의 |
| AI 프로필 이미지 | 실제 이미지 생성 또는 준비한 목업 이미지 무작위 배정 중 선택 | 아직 미결정 |
| 내 정보 | 현재 화면과 수정하기 연결 유지. 별도 추가 개발 범위로 잡지 않음 | 현 상태 유지 |
| 피드 | 단일 축제의 AI 프로필 생성 완료 사용자들을 표시. 참가자 수도 해당 사용자 수로 표시 | 프론트 + 백엔드 |
| 호감·매칭 | 호감 전송, 받은/보낸 목록, 상호 호감 시 성사 팝업과 대화 연결 | 프론트 + 백엔드 |
| 익명 대화 | 매칭된 두 사용자의 실제 메시지 송수신 | 프론트 + 백엔드 |
| SNS 공개 | 양쪽 동의 후 서로의 SNS를 확인하는 흐름 연결 | 프론트 + 백엔드 + Midnight |
| 과금·행사 운영 | 미구현으로 유지 | 이번 범위 제외 |

이번 범위에 **행사별 목록·행사 전환, 페이지네이션, 차단·비공개, 결제, 행사 종료 처리**를 추가하지 않습니다. 재접속/복구 고도화, 신고, 동시 요청 충돌 처리 등도 이번 해피패스 인계의 선행 작업으로 요구하지 않습니다.

## 최종 역할 분담과 공개 범위

- **백엔드:** 프로필·피드·호감 저장·상호 매칭 판정·대화방·메시지를 처리합니다. 기존 Midnight 호감/매칭 회로는 이번 데모에 연결하지 않습니다.
- **Midnight + 암호화 처리:** 민감한 SNS 정보의 공개 조건과 양측 동의 검증에 집중합니다. 구체적인 계약·키 전달 구현은 백엔드·Midnight 담당자가 함께 설계합니다.
- **프론트엔드:** 백엔드의 매칭 결과와 SNS 공개 승인 결과를 받아 화면에 표시합니다.

받은 호감 탭과 ‘나에게 호감 보낸’ 필터를 유지합니다. 상대방에게 받은 호감의 가명 프로필을 보여주며, 관리자에게 가명 프로필 사이의 호감 관계가 보이는 것도 허용합니다. 호감 관계 자체의 비공개는 이번 목표가 아닙니다. 핵심은 SNS를 관리자에게 노출하지 않고 서로 동의한 상대에게만 공개하는 것입니다.

AI 인상 문구 직접 수정은 구현하지 않습니다. 미리보기 후 공개 처리는 기존 화면을 백엔드에 연결할 때 함께 처리하며, 별도 프론트 누락 기능으로 분류하지 않습니다.

첨부 사업계획서의 ‘매칭 전 호감 비공개’, ‘AI 결과 직접 수정’, ‘Midnight 매칭 판정’ 설명보다 위의 최신 합의가 이번 MVP 기준입니다. 원본 PDF 자체는 수정하지 않았습니다.

## 백엔드 담당자와 우선 맞출 내용

### 1. 프로필과 피드

- 데모의 두 사용자를 구분할 사용자 ID와 프론트에서 현재 사용자를 지정하는 방법.
- 프로필 입력 데이터: 닉네임, 나이, 성별, MBTI, SNS ID, 자기소개, 분석용 사진.
- AI 결과 데이터: 인상 소개 4줄, 키워드, 프로필 이미지 URL, 프로필 생성 완료 여부.
- 프로필 저장/조회와 단일 축제 피드 조회의 요청·응답 형태.
- 참가자 수는 **AI 프로필 생성이 완료된 사용자 수**로 반환. 단순 접속자 수나 예시 카드 수를 쓰지 않음.
- SNS ID는 공개 피드 데이터에 포함하지 않고 SNS 공개 단계에서 사용.

내 정보 화면은 새로 설계하지 않습니다. 기존 화면이 저장된 프로필을 사용할 수 있도록 데이터만 같은 기준으로 맞춥니다.

### 2. 호감과 매칭

- 누가 누구에게 호감을 보냈는지 저장하고 받은/보낸 목록을 반환.
- 두 사용자가 서로 보냈을 때 매칭 완료와 대화방 식별자를 반환.
- 프론트가 매칭 완료를 받으면 성사 팝업을 표시하고 해당 대화로 연결.
- 상대방이 나중에 호감을 보낸 경우에도 현재 화면에서 매칭을 알 수 있도록 갱신 방법 합의. 구체적인 폴링/실시간 기술 선택은 담당자와 결정.

### 3. 익명 대화

- 매칭된 두 사용자가 같은 대화방에 접근하는 방법.
- 메시지 전송, 목록 조회, 상대방 메시지 수신 방법.
- 메시지에 필요한 최소 정보: ID, 대화방 ID, 보낸 사용자, 본문, 시간.

읽음 고도화·이력 페이지네이션·차단·신고·별도 대화 종료 기능은 이번 작업 목록에 추가하지 않습니다.

## AI 이미지 방식: 결정이 필요한 한 가지

**Gemini API를 이용한 실제 인상 분석은 진행할 방향**입니다. 데모 중 프로필 이미지까지 생성할지는 아직 확정하지 않았습니다.

| 선택지 | 데모 동작 | 보여줄 수 있는 범위 / 필요한 작업 |
|---|---|---|
| 실제 이미지 생성 | 사용자 사진 → 인상 분석 + 프로필 이미지 생성 → 피드 표시 | 사진 기반 개인화 이미지까지 시연. 이미지 생성 호출·결과 수신·대기 화면 연결 필요 |
| 미리 준비한 목업 무작위 배정 | 사용자 사진 → 실제 인상 분석 + 준비된 이미지 중 하나 배정 → 피드 표시 | 이미지 생성 연동을 생략하고 분석·매칭 흐름 시연에 집중. 이미지 자체는 사용자 사진 기반 결과가 아님 |

공통으로 밝은 파스텔 배경·밝은 의상의 이미지 방향을 유지합니다. 목업을 선택하면 배정한 이미지 ID를 프로필에 저장해 화면을 오갈 때마다 이미지가 바뀌지 않게 합니다. 목업을 실제 사진 기반 생성 결과로 설명하지 않습니다.

선택 기준은 **이번 시연에서 사진 기반 이미지 생성 자체까지 보여줄 것인지**입니다. 방식이 정해지기 전까지 둘 다 구현할 필요는 없습니다. 실제 생성의 모델·호출 시간·비용은 아직 이 문서에서 확정하지 않습니다.

Gemini 연동 시에는 API 호출 담당, 사진 전달 방식, 소개/키워드/이미지 응답 형태만 먼저 맞춥니다. 사진 처리·삭제 관련 화면 문구는 실제 구현에 맞춥니다.

## SNS 공개: 백엔드·Midnight 공동 협의

이번에 구현할 흐름은 **공개 요청 → 상대 동의 대기 → 양쪽 동의 완료 → 서로 SNS 확인**입니다. 매칭 자체를 SNS 공개 동의로 처리하지 않습니다.

맞출 항목은 다음 네 가지입니다.

1. 사용자·매칭 ID와 Midnight 측 참여자 식별자를 연결하는 방법.
2. 동의 상태를 어느 쪽에서 기록/검증하고 프론트에 어떤 완료 상태를 전달할지.
3. SNS 정보를 암호화·보관·전달하는 담당과 상대방이 확인할 수 있게 되는 시점.
4. 데모 참가자에게 필요한 계약 초기 상태를 어떻게 준비할지. 실제 QR/티켓 발급 화면을 추가하는 작업은 아님.

기존 계약의 `revealContact`는 매칭 참여자의 암호문 게시 기능이며 별도 양측 공개 동의를 보장하지 않습니다. 담당자와 이번 데모에서 양측 동의를 어떤 경로로 연결할지 정해야 합니다. 호감·매칭 판정은 백엔드에서 처리합니다. 기존 `revealContact`가 계약의 `matches`에 의존하므로, 백엔드에서 성립한 매칭을 SNS 공개 자격과 어떻게 연결할지는 Midnight 담당자와 설계합니다. 이를 위해 기존 on-chain 호감 흐름 전체를 프론트에 연결하는 것은 이번 범위가 아닙니다.

SNS를 관리자에게도 숨기려면 Midnight 사용만으로는 충분하지 않습니다. SNS를 서버로 보내기 전에 암호화하고 서버가 복호화 키를 갖지 않는 방향으로 설계하며, 실제 방식은 담당자와 확정합니다. 현재 UI의 “관리자도 확인할 수 없어요”는 이 암호화·키 관리 구현과 일치시킵니다. 이는 추가 운영 기능이 아니라 이번 SNS 공개 흐름의 설명과 구현을 맞추는 항목입니다.

## 작업 순서

1. 백엔드와 사용자 ID, 프로필·피드·호감·매칭·대화 데이터 형식 합의.
2. AI 이미지 방식 선택, Gemini 실제 인상 분석 연결.
3. 프로필 저장과 단일 축제 피드 연결. 생성 완료 사용자 수 표시.
4. 두 사용자 간 호감·매칭·성사 팝업·익명 대화 연결.
5. 백엔드·Midnight와 SNS 양측 동의 및 공개 연결.
6. 아래 해피패스로 시연 확인.

## 데모 완료 기준

- 사용자 A와 B가 프로필을 만들면 피드에 표시되고 참가자 수에 반영된다.
- 실제 분석 문구와 선택한 방식의 이미지가 각 프로필에 표시된다.
- A만 호감을 보냈을 때는 대화가 열리지 않는다.
- B도 호감을 보내면 서로 매칭되고 성사 팝업에서 대화를 시작한다.
- A와 B가 메시지를 주고받는다.
- 한쪽만 SNS 공개에 동의하면 대기하고, 양쪽이 동의하면 서로 SNS를 확인한다.

QR 인증, 다중 행사, 과금, 차단·비공개, 추가 내 정보 기능은 완료 기준에 포함하지 않습니다.

## 현재 코드 참고

- `web/src/state/session.tsx`: 지금은 메모리 기반 프로필·호감·메시지·동의 상태. 백엔드 연동 교체 지점.
- 사진 버튼은 준비 상태만 변경하며 파일 선택·업로드는 아직 없음. 분석도 현재는 타이머와 고정 예시.
- SNS 요청은 현재 전체 메시지 4개부터 노출되는 데모 조건. 이를 과금/무료 대화 정책으로 확대하지 않음.
- `/preview`의 예시와 동의 시뮬레이션은 화면 확인용. 실제 연동 여부와 구분.
- 기존 프론트 빌드 및 Chromium/WebKit 64개 테스트 통과. 실제 서버·Gemini·Midnight 연동 테스트는 별도 진행 예정.
